BootManagerV2 - Codex opdracht: verwerk Pi veldtest met echte bootdata

Context
-------
We hebben op vrijdag 29 mei 2026 een eerste veldtest uitgevoerd met BootManagerV2 op de Raspberry Pi aan boord van de boot.

Situatie vooraf:
- De Raspberry Pi was thuis ingericht en op master gezet.
- De Pi draait BootManagerV2 via Docker Compose.
- De Pi stond op master met commit:
  1db5534 Document sudo requirement for Pi reset script
- De database was vooraf praktisch leeg:
  - De bootstrap/eerste onboarding was uitgevoerd.
  - Er was dus minimaal een account/bootcontext aanwezig.
  - Verdere meetdata was nog niet bewust opgebouwd.
- Alle NMEA-apparatuur stond eerst uit, zodat we gecontroleerd konden starten.
- Doel van deze test:
  - vaststellen of de Pi in het bootnetwerk goed opstart;
  - vaststellen of de Pi echte bootdata ontvangt;
  - vaststellen of bootmanager-ingest echte data doorstuurt naar bootmanager-web;
  - vaststellen of bootmanager-web de berichten accepteert, parseert, interpreteert en opslaat;
  - vastleggen welke aandachtspunten en vervolgstories hieruit volgen.

Belangrijk:
- Latere logboekstories na PR #65 waren voor deze test niet belangrijk.
- Voor deze test was vooral belangrijk dat de Pi de database-resetfunctionaliteit had en op een stabiele master stond.
- De Pi hoort alleen master te pullen, nooit feature branches.

Waarneming:

docker compose logs --since 5m bootmanager-web | grep -i -A 2 -B 1 "warn" | head -80

Outputfragment:

warn: BootManager.Application.NetworkMessages.Services.NetworkMessageService[0]
NMEA0183 GGA-interpretatie mislukt: GGA-fixkwaliteit ontbreekt of ongeldig ('0'). Alleen fixkwaliteit > 0 wordt opgeslagen.

Dit herhaalde meerdere keren.

Conclusie:
- YD/GGA wordt ontvangen en geparset.
- GGA-positie wordt niet als geldige positie opgeslagen wanneer fixkwaliteit 0 is.
- Dit is functioneel verdedigbaar: fixkwaliteit 0 betekent geen geldige GPS-fix.
- Dit is geen crash en geen API-fout.
- Dit is wel een veldtestobservatie:
  - de applicatie waarschuwt veelvuldig;
  - bij veel GGA-berichten zonder fix kan dit tot logruis leiden;
  - later kan bekeken worden of dit als Debug/Information gelogd moet worden, of dat waarschuwingen gebundeld/throttled moeten worden.

Status:
- Ontvangst/parsing: groen.
- GGA valid-position-opslag: geel zolang fixkwaliteit 0 is.
- Logniveau/ruis: aandachtspunt.

Vervolgstory mogelijk:
- Logniveau en throttling voor verwachte NMEA-validatie-afwijzingen verbeteren.
- Dashboard/diagnostics tonen: aantal ontvangen GGA, aantal geldige GPS-fixes, laatste fixkwaliteit.
- Onderscheid maken tussen “technisch fout” en “verwachte data zonder geldige fix”.

Open punten / observaties
-------------------------
1. sqlite3 ontbreekt op de Pi en in de container
   - Directe SQL-inspectie van aantallen records kon daardoor niet plaatsvinden.
   - Dit is geen applicatiefout, maar wel een beheeraandachtspunt.
   - Mogelijke story: Pi diagnostics/runbook uitbreiden met sqlite3-installatie of alternatief.

2. GGA-fixkwaliteit 0 geeft veel warnings
   - GGA wordt technisch ontvangen en geparset.
   - Bij fixkwaliteit 0 wordt geen geldige positie opgeslagen.
   - Dit is logisch gedrag, maar kan veel logruis geven.
   - Mogelijke story: logniveau/throttling verbeteren voor verwachte validatie-afwijzingen.

3. Positieflow vraagt later nog inhoudelijke validatie
   - Er zijn PositionMeasurements inserts gezien.
   - Tegelijk waren er GGA-fixkwaliteit-0 warnings.
   - Mogelijke story: diagnostics tonen welke position sentences geldig zijn, met laatste fixkwaliteit en bron.

4. UI-validatie is nog niet uitgevoerd
   - Deze test keek naar containers, logs, API en opslag.
   - Er is nog geen browser-/dashboardtest uitgevoerd om te controleren of metingen correct zichtbaar worden.
   - Mogelijke story/test: UI live dashboard of data-overzicht valideren tegen opgeslagen metingen.

5. Meetwaarden moeten later inhoudelijk worden vergeleken met boordapparatuur
   - Voorbeeldwaarden zoals wind, heading en watertemperatuur lijken plausibel.
   - Er is nog niet gecontroleerd of deze exact overeenkomen met Raymarine/Axiom/instrumenten.
   - Mogelijke story/test: veldtestprocedure voor vergelijking BootManager versus boorddisplay.

6. Logvolume is hoog
   - Live logs liepen heel hard zodra apparatuur aan stond.
   - Mogelijke story: loggingprofiel voor veldtest/productie verbeteren, bijvoorbeeld minder EF SQL logs, compactere ingest samenvatting, aparte diagnostics view.

7. Databasegroei/WAL monitoring
   - bootmanager.db-wal werd meerdere MB groot tijdens korte test.
   - Dit past bij actieve writes, maar vraagt later aandacht voor langdurige logging, WAL-checkpointing, retentie en opslaglimieten.
   - Mogelijke story: dataretentie en database health monitoring voor Pi.

8. Capture logs / NDJSON zijn in deze test niet apart gevalideerd
   - We zagen Ingest en Web logs, maar hebben niet apart gecontroleerd of capture logs op het volume correct ontstaan.
   - Mogelijke story/test: capture-loglocatie, rotatie en replaybaarheid valideren.

9. NMEA 0183 versus NMEA 2000 terminologie
   - De fysieke bron is NMEA2000/SeaTalkNG via gateway.
   - De applicatie ontvangt op dit moment NMEA 0183 sentences van de Yacht Devices gateway.
   - Documentatie moet dit correct formuleren: echte bootdata uit NMEA2000-netwerk via gateway, ontvangen/verwerkt als NMEA 0183 UDP-sentences.
